# BOTH build systems, hash-pinned, for the interpreter that builds either tree.
#
# This is the file that makes stage 3 different from the other two images.  Stage 1
# has no build system at all; stage 2 has Meson and asserts at image-build time
# that setuptools, distutils and pkg_resources cannot be imported.  This stage has
# to build the ORIGINAL as well, because a candidate's claim that "the setuptools
# build ships this and the Meson build does not" is worth nothing unless the
# setuptools build is right here to answer for itself.
#
# That reads like a loophole and is the opposite of one.  Stage 1 has already judged
# whether setuptools left the submission, with both trees open and a reviewer, and a
# failure there scores the submission zero before this image starts.  What this image
# adds is the ability to ask State A a question at grading time.
#
# Everything below must therefore be importable, and a missing one is fatal.  A
# stage-3 image without setuptools would not fail visibly -- it would make every
# candidate fail on the original, which the adjudicator reads as "found nothing",
# which pays the submission all 60 points.  Stage 2 pins the same two versions for
# the neighbouring reason: its recordings came from that build.
#
# ---------------------------------------------------------------------------
# For the ORIGINAL
#
#   setuptools    State A's `[build-system] requires`.  69.0.3 is the release
#   wheel         contemporaneous with pycryptodome 3.20.0 (January 2024), which is
#                 the same reason SOURCE_DATE_EPOCH is pinned to 2024-01-09: what a
#                 candidate compares is what State A's build produced then, and a
#                 setuptools two years newer would produce a different METADATA
#                 block, a different RECORD and possibly a different wheel tag,
#                 none of which the migration is responsible for.
#
# For the SUBMISSION
#
#   meson         the same four versions stage 2 grades against, to the byte.
#   meson-python  A submission that built one way for stage 2 and another way here
#   ninja         would be graded on two different artifacts, and a divergence
#   patchelf      between them would be this stage's own doing.
#
# For BOTH
#
#   build         the PEP 517 front end.  Both trees are PEP 517 packages, so
#                 `python -m build --wheel --no-isolation` builds either one and the
#                 backend it dispatches to is the only difference.  That is what
#                 makes a comparison between two build systems mean anything here:
#                 the command, the flags and the front end are identical on both
#                 halves of it.
#   pyproject_hooks, pyproject-metadata, packaging
#                 the front end's and meson-python's own closure, pinned rather
#                 than resolved.
#
# ---------------------------------------------------------------------------
# Deliberately absent: pycryptodome, and pytest.
#
# pycryptodome because the only Crypto that may exist during a run is the one a
# submission's own wheel installs into a scratch prefix; an importable one here
# would let a candidate measure the image instead of the build.  The Dockerfile
# asserts it is not importable.
#
# pytest because the candidate's stack is a separate file installed into a separate
# interpreter -- see requirements-candidate.txt.  The process that builds the trees
# does not share an interpreter with code an adversary wrote.
