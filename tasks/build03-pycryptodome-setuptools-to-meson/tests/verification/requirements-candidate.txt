# The candidate's test stack for stage 3, hash-pinned.
#
# This is not pycryptodome's dependency list -- it has none, which is part of why
# it is a good subject for a build-system migration -- it is what a candidate's
# test file may import beyond the standard library and srbcrypto.  Both trees get
# the same versions from the same virtual environment, because a candidate whose
# pytest differed between the two halves of a comparison would not be comparing the
# two build systems.
#
# The same five versions build01's and fw01's stage 3 pin, for the same reason: a
# benchmark should not run two pytests.  Python here is 3.12, so neither
# exceptiongroup nor tomli is in the closure.
#
# Installed into /opt/venv, which is NOT the interpreter that builds either tree.
# The build interpreter is the system one, named by $SRB_BUILD_PYTHON, and it is
# where both backends live -- see requirements-toolchain.txt.  The separation is
# the same one build01 makes: the process orchestrating the stage does not share an
# interpreter with code an adversary wrote.  It has a second effect here that it
# does not have in a C task, and the effect is the point: setuptools is installed
# in the build interpreter and is NOT importable from a candidate's own process, so
# `import setuptools` inside a test file answers the same way on both trees.
#
# Deliberately absent: everything else, and pycryptodome most of all.  A candidate
# reaches this library through srbcrypto -- a wheel, the install it produces, the
# compiled objects in it, and the library's own 39,245-test suite run against it --
# and the only Crypto that exists during a run is the one the tree under test
# built.  An importable one in this venv would let a candidate compare a build
# against the image rather than against the other build.
