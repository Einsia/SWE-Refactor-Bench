# The scan's runner, and nothing else.
#
# Four packages, hash-pinned, --no-deps: this is a test runner for 663 checks
# that open files and hash them.  Nothing here can import the submission, and that
# is the point of keeping the list this short -- the moment an HTTP client or a
# framework appears in this image, a scan module could start a service, and stage
# 1's whole claim is that it cannot.
#
# Note what is *conspicuously* absent for this task in particular: no `meson`, no
# `meson-python`, no `build`, no `setuptools`, no `wheel`.  A submission is a
# Python package with a PEP 517 backend, so the one-line mistake available here is
# `pip install /opt/workspace` in a scan module -- which would execute the
# submission's build backend, in the stage whose entire claim is that it cannot
# execute anything.  The stage-1 Dockerfile also deletes setuptools and pip's
# wheel machinery after installing these four, so the import fails rather than the
# build succeeding somewhere nobody is looking.
#
# The versions and hashes are the ones tests/behavioural/requirements-target.txt
# already pins, so the scan runs on the same pytest the behavioural suite does and
# there is one version of the runner to reason about across the two stages.  Both
# lists pin both the wheel and the sdist digest for each name: pip verifies
# whichever file it selects, and pinning only one of the two fails on an image
# that prefers the other.
#
# `packaging` is here at a version far newer than pytest needs, and that is the
# behavioural stage's constraint leaking in rather than a choice: `build 1.5.0`
# requires packaging>=24.0, and the two files hold the same version on purpose.
# Nothing in the scan imports it directly -- pytest does.
