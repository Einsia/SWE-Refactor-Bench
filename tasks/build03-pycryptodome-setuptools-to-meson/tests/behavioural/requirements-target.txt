# The new toolchain, the test runner, and the project's own vectors.
#
# Installed with --require-hashes, so every line below is a version *and* the
# bytes of that version.  This matters more here than in a normal project: the
# whole stage rests on "the submission's build succeeded against a fixed
# toolchain", and a toolchain that silently moved between the run that recorded
# data/ and the run that grades a submission turns a measurement into a
# coincidence.
#
# What is here, and why each line has to be:
#
#   meson, ninja        the build system the migration targets, and its backend.
#   meson-python        the PEP 517 backend a Meson-built Python package needs.
#                       Never invoked by name anywhere in this suite -- the suite
#                       only ever says `python -m build --wheel --no-isolation`
#                       and lets the submission's pyproject.toml choose.  It is
#                       installed because --no-isolation means pip will not fetch
#                       a backend, so an absent one would fail every submission.
#   patchelf            meson-python rewrites RPATHs through it.  These 41
#                       objects link nothing but libc, so it will likely never
#                       fire -- but a backend that wants it and cannot find it
#                       fails the build, and that failure would read as the
#                       submission's fault.
#   build, pyproject_hooks, pyproject-metadata, packaging
#                       the front end and what it imports.
#   pytest, iniconfig, pluggy
#                       the runner for the eleven pytest modules.
#   setuptools, wheel   State A's backend, at the release contemporaneous with
#                       pycryptodome 3.20.0.  See the block below.
#
# Why State A's backend is installed in the image that grades the migration away
# from it.
#
# This stage grades behaviour preservation, and every expectation it grades was
# recorded from State A -- the wheel's 336 members, the 277 exported symbols per
# object, the four artefact counts under a crippled compiler, the 39,245 self-test
# ids.  An image that cannot build State A cannot rebuild the tree those numbers
# came from, which means the suite cannot be run against its own oracle: the
# reference for "correct" fails the stage that defines it, and every number in
# data/ is an assertion nothing in this image can check.
#
# Leaving them out would also be load-bearing for a claim this stage does not
# make.  "The submission does not need setuptools" is a question about whether the
# migration happened, and it belongs to stage 1's `setuptools_retired` gate, which
# reads both trees with a reviewer and whose failure scores the submission zero
# before this image runs.  The one check here whose subject is that -- cleanliness
# `test_the_wheel_was_built_with_the_backend_the_tree_declares` -- is recorded at
# weight 0.0 and scores nothing either way.  So their absence would buy a detection
# this stage does not perform, at the price of the stage being unable to build its
# own reference.
#
# `python -m build --no-isolation` is why both backends have to be installed
# rather than resolved: the front end will not fetch a backend, so whichever one a
# tree declares in `[build-system] requires` must already be here.  Installing
# both is what makes the front end neutral -- the tree's own pyproject.toml picks,
# and the harness never names a backend.
#
# 69.0.3 and 0.42.0 are the releases contemporaneous with pycryptodome 3.20.0
# (January 2024), the same reason SOURCE_DATE_EPOCH is pinned to 2024-01-09.
# data/wheel.json records `Generator: bdist_wheel (0.42.0)` and the filename
# `pycryptodome-3.20.0-cp35-abi3-linux_x86_64.whl`; a setuptools two years newer
# would produce a different METADATA block, a different RECORD and possibly a
# different tag, none of which the migration is responsible for.  These are the
# same two versions, to the byte, that ../verification/requirements-toolchain.txt
# installs for the same purpose -- stage 3 also has to build State A.
#
# One consequence to keep in view: `import distutils` resolves, through
# setuptools' vendored copy and its `distutils-precedence.pth`.  Nothing in this
# suite asserts otherwise; the Dockerfile checks that both backends are reachable
# through the front end, which is the assertion this stage's numbers rest on.
#
# What is deliberately absent: pycryptodome-test-vectors.
#
# It is absent for a narrower reason: the vectors *are*
# needed -- without them Crypto.SelfTest collects 3,603 instances instead of
# 42,784, and the module that would notice a wrong compiler flag never runs --
# but the only distribution PyPI has for it is an sdist, and `pip install` of an
# sdist prepares its metadata in an isolated environment that fetches its own
# unpinned build backend.  That is a resolver deciding what goes into an image
# that claims to be reproducible, which is the thing --require-hashes exists to
# prevent.  It is 443 data files and no code, and
# `Crypto/SelfTest/loader.py` reaches it with `import pycryptodome_test_vectors`
# and `os.path.dirname(__file__)` -- no metadata, no entry points -- so the
# Dockerfile fetches the sdist, checks this digest, and copies the package
# directory into site-packages:
#
#     pycryptodome-test-vectors==1.0.14
#     sha256:d437b44a35dcafc0626c3561bfb1b506a1b7c7445cc5fb9d36e2374161bc9a37
#
# and then asserts the import resolves and a vector actually loads.
#
# Both the sdist and the wheel digest are listed for each package.  pip verifies
# whichever file it selects, and a list that pins only one of the two fails on an
# image where the other is preferred -- a failure that would look like a network
# problem and cost a submission its whole score.
#
# pytest, iniconfig, packaging and pluggy are also pinned, to these same
# versions and digests, by ../audit/requirements-scan.txt.  One runner
# across both stages, so a check that behaves one way in the scan cannot behave
# another way here.
