TLS material for the harness, held outside the repository.

These live here, outside /workspace/repo, and an identical copy lives in the
verifier image. The repo ships its own copies under tests/data/, but those belong
to the submission and are fair game for it to edit; what TLS is graded against
must not be.

Three (certificate, key) pairs, chosen so that each one takes a different branch
through the baseline's key loader. It accepts a private key by scanning the PEM
file for the first item it recognises:

    pemfile::Item::RSAKey   -- a traditional "BEGIN RSA PRIVATE KEY" body
    pemfile::Item::PKCS8Key -- "BEGIN PRIVATE KEY", any algorithm
    pemfile::Item::ECKey    -- "BEGIN EC PRIVATE KEY"

rustls-pemfile treats those as separate container formats, so a port that wires
up only the PKCS#8 case passes one of these sessions and fails another.

    cert_rsa.pem + key_pkcs8.pem   RSA 4096, key as PKCS#8   -> PKCS8Key
    cert_rsa.pem + key_pkcs1.pem   the same key, traditional -> RSAKey
    cert_ec.pem  + key_ec.pem      ECDSA secp384r1, PKCS#8   -> PKCS8Key

Provenance: cert_rsa.pem, cert_ec.pem, key_pkcs8.pem and key_ec.pem are
miniserve's own test certificates, taken unchanged from tests/data/ in the 0.27.1
source tree (MIT, generated by the generate_tls_certs.sh script beside them).
Both certificates are self-signed for CN=localhost and valid from 2023-04-16 to
2033-04-13, so nothing here expires during the useful life of this task.

key_pkcs1.pem is derived here rather than copied, and the reason is worth
recording: upstream's file of that name is *not* PKCS#1. It was produced with
`openssl rsa -in key_pkcs8.pem -out key_pkcs1.pem`, which under OpenSSL 3 writes
PKCS#8 again -- the two upstream files are byte-identical, so the RSAKey branch
upstream believes it tests is never reached. The copy here was produced with
`openssl rsa -traditional`, so it really does begin with "BEGIN RSA PRIVATE KEY".

Note also that upstream's cert.pem has no matching key in the tree at all -- it
is used only by a negative test that checks the error message for a missing key
file -- so it is deliberately not shipped here. Pairing it with any of these keys
produces a handshake that fails with BAD_SIGNATURE.

The harness connects with verification disabled. What is being graded is that a
TLS listener exists, that it was configured from these files in these formats,
and that it serves the same bytes as the plaintext listener -- not the trust
chain.
