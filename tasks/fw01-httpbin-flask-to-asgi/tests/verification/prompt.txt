TASK {{task}} -- find what the migration got wrong.

httpbin is an HTTP request-and-response service: you send it a request, it tells
you what it received, or returns exactly what you asked for. The original is a
synchronous Flask/Werkzeug application served by gunicorn with gevent workers,
with its OpenAPI surface generated by flasgger. The submission is supposed to be
the same service, reimplemented natively on Starlette and uvicorn, with the old
stack removed and every observable behaviour preserved.

Preserved means byte for byte where it can be: same status codes, same bodies
(JSON pretty-printed with two-space indentation, sorted keys, trailing newline),
same semantic headers. It has already been checked that the migration is real and
that a large recorded corpus of requests still gets the right answers. Your job
is the part that corpus cannot do: find a request nobody thought to record.

THE TWO TREES

  {{original}}     the original service, Flask/WSGI
  {{submission}}   the submission, which claims to be the same service on ASGI

Your tools address these by name: {{roots}}. The submission is the root called
`workspace`. Both are complete repositories, and both are read-only to you --
you attack them over HTTP, not by editing them.

HOW A CANDIDATE IS RUN

Write a pytest file and hand it to `try_test`. For each tree, the runner installs
that tree into a clean virtualenv, starts it through its own production entry
point, waits for it to answer, and runs your file against it. You are told the
outcome on each tree separately.

Your file gets one thing from the environment:

    SRB_BASE_URL   e.g. http://127.0.0.1:8080 -- the running target

`httpx` is available, and so is the standard library. Nothing else is. Do not
import the tree under test, and do not read its files from inside the test: an
in-process import measures a module, and what is being graded is a service. Send
requests to SRB_BASE_URL and assert on what comes back.

Exit status is the verdict: zero means your test passed against that tree,
non-zero means it failed. pytest does this for you.

WHAT A USEFUL CANDIDATE LOOKS LIKE

It has to pass on the original and fail on the submission. Both halves matter,
and the first is where most attempts die: a test that fails on both trees has
found a bug in the test, or a behaviour the original never had. Run every idea --
you have budget for many, and one call tells you which of the four outcomes you
got.

Then it has to assert on something that was promised. The scope below is httpbin's
public contract; a divergence outside it is thrown out on review no matter how
real it is, and you will have spent the budget for nothing. Header name casing,
the Server header, reason phrases, chunked-vs-Content-Length on ordinary
responses: all genuinely different between these two servers, all excluded, none
worth a candidate.

WHERE REWRITES OF THIS KIND ACTUALLY FAIL

Not on the main path. `/get` and `/post` work in every submission, because they
are the first thing anyone tries and the first thing anyone tests. What gets left
out is:

  * The second and third parameter of an endpoint that mostly gets called with
    one. Werkzeug and Starlette disagree about how a route with an optional
    trailing segment matches, about trailing slashes, and about what a
    percent-encoded separator inside a path segment means.
  * Werkzeug behaviour the original inherited without writing down. Its
    MultiDict's treatment of repeated keys. Its cookie serialisation. Its
    handling of a malformed Content-Type, a header that appears twice, a body
    that is not valid UTF-8. The original's author did not implement these; the
    submission's author had to.
  * Anything with a seed. `/bytes`, `/stream-bytes` and `/range` are seeded
    pseudo-random: the same seed must produce the same bytes. Reproducing a
    generator exactly is easy to get almost right.
  * Whole features that are documented and rarely used. Digest auth with
    `qop=auth-int`. `stale_after`. `/response-headers` with a repeated
    parameter. `/status/200:0.1,500:0.9`. The `show_env` header set.
  * Streaming, which is where a synchronous implementation hiding behind an async
    signature becomes visible: whether the response declares a Content-Length,
    whether the chunks arrive over time, whether one slow request blocks
    another.
  * Error paths. What the original returns for a request that is wrong in some
    small way -- a bad range, a non-integer where a number goes, a value out of
    bounds, a method the route does not take.

Read the original's implementation of whatever you are attacking before you write
the test. The point is not to guess what the original does; it is there, and it is
the standard your test has to meet first.

REPORTING

If you find a divergence that holds up, report it with the candidate name and a
description of what the submission gets wrong in terms of behaviour, plus which
part of the contract it violates.

If you do not, report that you found nothing, and say what you tried and where
you looked. That is a real result -- it is what a sound submission is supposed to
produce -- and a claim you cannot support is worth nothing more.
