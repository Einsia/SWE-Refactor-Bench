# Migrate httpbin from Flask/WSGI to a pure ASGI stack

You are working in `/workspace/repo`, a frozen checkout of **httpbin 0.10.2** — the
HTTP request-and-response service. It is a synchronous **Flask + Werkzeug (WSGI)**
application, served in production by **gunicorn with gevent workers**, with its
OpenAPI surface generated by **flasgger**.

Your job is to migrate the **entire repository** to a **native ASGI** application
built on **Starlette + uvicorn**, and to retire the old stack completely — while
keeping the service's observable behaviour identical.

This is a behaviour-preserving migration. **Do not add features, do not remove
endpoints, and do not change the public HTTP contract.** Every response the
service produces today it must still produce, byte for byte, where this document
says so.

---

## 1. The two states

|                     | State A (now)                          | State B (required)                     |
| ------------------- | -------------------------------------- | -------------------------------------- |
| Web framework       | Flask 2.2.5                            | Starlette 0.41.3                       |
| HTTP layer          | Werkzeug 2.2.3 (WSGI)                  | native ASGI 3                          |
| Server              | gunicorn 21.2 + gevent workers         | uvicorn 0.32.1                         |
| Concurrency model   | synchronous, greenlet-monkeypatched    | `async`/`await` on the event loop      |
| OpenAPI / Swagger UI| flasgger 0.9.7.1                       | your own implementation                |
| Helper libraries    | `six`, `decorator`                     | removed                                |
| Templating          | Jinja2 (via Flask)                     | Jinja2 (directly) — still allowed      |

### Retired dependencies

These distributions must not appear anywhere in the delivered project — not as a
declared dependency, not as an import, not vendored into the tree, and not named
in the packaging manifests, the lockfile, the `Dockerfile`, or the `Procfile`:

```
flask  werkzeug  flasgger  quart  six  decorator
gunicorn  gevent  eventlet  greenlet  asgiref  a2wsgi
```

`asgiref` and `a2wsgi` are listed explicitly because wrapping the existing WSGI
application in a WSGI-to-ASGI bridge is **not** a migration. Neither is
re-implementing the protocol yourself: what is asked for is an application that
speaks ASGI natively, not one that speaks WSGI behind an adapter you wrote.

That is judged by what the application *is*, not by which identifiers appear in
it: `httpbin:app` is imported and asked whether it is awaited as
`await app(scope, receive, send)`, and the request path is followed to see whether
a WSGI environ is being built and handed to something. A file that mentions
`start_response` or `PATH_INFO` in a comment, in a compatibility shim you do not
call, or in a test of your own is not the finding — a request being served through
those is. There is no token list to satisfy and nothing to gain from renaming.

### Retired means the library, not just the protocol

Everything above is about the protocol, and it draws its line at an adapter. There
is a second line, and it is the one that decides whether the old dependency is
actually gone.

Section 4 asks you to reproduce the current service's observable behaviour to the
byte, and some of that behaviour comes from inside the retired libraries: how
repeated query keys collapse, how header names are cased, which characters survive
URL quoting, which `Location` values stay relative. Reproducing those **effects**
is the job. What does not count as retiring the dependency is reproducing them by
transplanting the retired distribution's own modules — lifting `werkzeug.http` or
`werkzeug.datastructures` into the tree, function for function under their upstream
names, is the dependency renamed rather than removed, and it is read that way
however well the service then behaves.

The measure is the size of the surface, not the presence of a name. The current
service imports seven names from Werkzeug in total; `grep -rn 'from werkzeug'
httpbin/` shows you which, across two files and one version fallback. Writing the
handful of helpers those seven call for — a date
formatter over `email.utils`, a quoting call with the right safe set, whatever
multidict the new stack already hands you — is the migration. Arriving at a module
that is Werkzeug's parsing layer with the imports stripped off is not, even if
every response matches.

### Available dependencies

The environment is **offline**. The only installable packages are the pinned
wheels in `/opt/wheelhouse`, which is exactly the wheel set the grader uses:

```
starlette  uvicorn  jinja2  python-multipart  brotlicffi  pyyaml
setuptools  wheel        (build backend — keep the project setuptools-based)
pytest  pytest-timeout  httpx        (for your own testing)
```

Anything outside that list cannot be installed and must not be declared.

## 2. What "migrated" has to mean

Evaluation happens in **separate, offline containers**. Nothing you build in place
is trusted: the project is reinstalled from your source against `/opt/wheelhouse`,
in a clean environment, and exercised from the outside.

So the deliverable is judged as a repository, not as a diff. Six things have to be
true of it:

1. **It installs.** `pip install --no-index --find-links /opt/wheelhouse
   /workspace/repo` succeeds in an empty venv, and the resulting dependency
   closure contains none of the retired distributions.
2. **The old stack is gone from the source**, not merely unreferenced from the
   happy path: no imports, no vendored copies, no WSGI protocol surface, no paths
   named after it, and no mention in the packaging manifests, the lockfile, the
   `Dockerfile` or the `Procfile`. Prose (`*.md`, `*.rst`) and the contents of
   `httpbin/templates/` and `httpbin/static/` are the exception — describe the
   migration in documentation freely.
3. **`httpbin:app` is a real ASGI 3 application** — a callable invoked as
   `await app(scope, receive, send)` — and importing it loads none of the retired
   frameworks.
4. **The repository publishes a working way to start itself, and that is the way
   it gets started.** Both the behavioural and the verification stage boot the
   service through an entry point the project itself publishes, trying them in
   this order and using the first that answers HTTP: `httpbin.bash`, a console
   script installed by your built distribution, the `Procfile`'s `web:` line.
   Keeping `httpbin.bash` working is the least surprising choice and it is the one
   State A ships, but moving start-up to a console script your own
   `pyproject.toml` declares is equally a published entry point. What does not
   count is a uvicorn command line someone would have to know to type: if nothing
   the repository publishes starts the service, it does not run.
5. **The new implementation is what actually serves traffic.** A correct ASGI port
   sitting beside a Flask app that still handles requests is not a migration, and
   neither is a Starlette shell delegating to the old code.
6. **The answers are computed.** The service will be asked for `/base64/<a nonce>`,
   `/bytes/<a computed length>` and `/basic-auth/<credentials invented at
   evaluation time>` — values no captured corpus contains. A lookup table pairing
   paths with literal status codes, a replayed response corpus, or any branch that
   behaves differently when it thinks it is being tested, is not a port of httpbin.

Points 2, 5 and 6 are reviewed by reading the repository, not by matching strings,
so there is no keyword list to satisfy and nothing to be gained from renaming
things. The question asked is whether the old implementation genuinely left and the
new one genuinely took over.

## 3. The reference oracle

The original application is installed, immutable, in `/opt/oracle`, and serves
the **unmodified State A behaviour** for as long as you need it:

```bash
httpbin-oracle &                       # listens on 127.0.0.1:8899
curl -sD- http://127.0.0.1:8899/get
```

It runs from its own copy of the original sources, so it keeps answering
correctly no matter how far you rewrite `/workspace/repo`. Use it as ground
truth: issue the same request to the oracle and to your server, and diff the
two responses. The behavioural suite that grades you was built the same way.

The oracle runs on Flask, Werkzeug and gunicorn/gevent — the exact stack you are
removing. It is a reference, not a target. Do not copy it into your deliverable.

`git log` holds a single baseline commit, so `git diff` and
`git checkout -- <path>` work against State A.

## 4. Behavioural contract

Every endpoint the service exposes today must keep working. That is roughly
**80 route/method combinations across 52 documented paths**, and the suite that
grades you exercises them end to end over real HTTP against your running server.

### Must be preserved exactly

* **Status codes**, for every documented and undocumented path, including the
  `/status/<codes>` weighted-choice forms and every special case in the
  status-code table (`301`–`308` redirects with their `Location`, `304` with an
  empty body, `401`/`407` challenges, `402`, `406`, `418`).
* **Response bodies, byte for byte.** JSON responses are pretty-printed with
  **2-space indentation and sorted keys, and end with a trailing newline** —
  matching the current output exactly. Streaming endpoints emit the same
  payloads in the same order.
* **Semantic headers**: `Content-Type` (including exact charset spelling and
  parameter order), `Content-Length` where the current implementation sets it,
  `Content-Encoding`, `Location` (**relative Locations stay relative** — the
  current app disables Werkzeug's URL autocorrection), `WWW-Authenticate`,
  `Proxy-Authenticate`, `Set-Cookie` (name, value, `Path`, and the absence of
  attributes the current app does not emit), `ETag`, `Cache-Control`, `Accept-Ranges`,
  `Content-Range`, `Vary`, `Link`, `X-Runtime`, and the `X-More-Info` easter eggs.
* **CORS behaviour** on every response, and the full `OPTIONS` preflight
  response, including `Access-Control-Allow-Origin` mirroring, `Allow-Methods`,
  `Max-Age`, and the echo of `Access-Control-Request-Headers`.
* **Request parsing**: query strings and forms with repeated keys collapse the
  same way (single value bare, repeated values as a list); multipart uploads,
  JSON bodies, and non-UTF-8 bodies (which are returned as a base64 `data:` URL)
  behave identically; the header dictionary is populated and filtered the same
  way, including the `show_env` behaviour for the proxy header set.
* **Authentication**: HTTP Basic, hidden Basic (404 on failure), Bearer, and
  the full **Digest** implementation — MD5 / SHA-256 / SHA-512, `qop=auth` and
  `qop=auth-int`, the `stale_after` cookie mechanism, nonce/opaque handling, and
  the `require-cookie` variant.
* **Deterministic payloads**: `/bytes/<n>`, `/stream-bytes/<n>` and
  `/range/<n>` must produce the **same bytes for the same seed** as they do
  today. They are seeded pseudo-random; reproduce the generator, do not invent
  one.
* **Compression**: `/gzip`, `/deflate`, `/brotli` — same encodings, same
  `Content-Encoding`, and bodies that decompress to the same JSON.
* **Range requests** on `/range/<n>`: satisfiable and unsatisfiable ranges,
  suffix and open-ended ranges, `416`, and the `duration`/`chunk_size` behaviour.
* **Templated pages**: `/`, `/html`, `/forms/post`, `/legacy`, `/robots.txt`,
  `/deny`, `/xml`, `/encoding/utf8`, and the images under `/image*` — same
  bytes, same content types.

### OpenAPI and Swagger UI

flasgger is gone, so you must serve this surface yourself:

* `GET /spec.json` returns the **Swagger 2.0** document, with the same
  `swagger`, `info`, `host`, `basePath`, `schemes` and `tags` metadata, and the
  same set of paths — each with the same methods, `tags`, `summary`,
  `description`, `parameters` and `produces` as today.
* `GET /` serves the Swagger UI page, `Content-Type: text/html; charset=utf-8`,
  loading its spec from `/spec.json`.
* Every asset the UI references must be served **by this application, from the
  same origin**. The environment is offline: a CDN reference is a broken page.
  The Swagger UI assets currently ship inside the flasgger wheel; you will need
  to bring them into the project. Serve them from a path that is not named
  after the retired package.

### Explicitly *not* part of the contract

These differ between any two HTTP servers and are never compared:

* the `Server` and `Date` headers;
* HTTP reason phrases (Werkzeug upper-cases some; uvicorn does not);
* header **name** casing, and the order of distinct header names;
* whether a response is delivered with `Content-Length` or
  `Transfer-Encoding: chunked` — *except* that the streaming endpoints
  (`/stream/<n>`, `/stream-bytes/<n>`, `/drip`) must genuinely stream and so
  must not declare a `Content-Length`;
* connection-management headers (`Connection`, `Keep-Alive`);
* the `X-Runtime` *value* (its presence and format are checked, not its timing).

### Async correctness

The point of the migration is a native-async service, and this is measured
behaviourally, not by inspection:

* Request handling must not block the event loop. `/delay/<n>`, `/drip`,
  `/stream/<n>` and `/stream-bytes/<n>` must `await` rather than sleep, and
  streaming responses must yield to the loop between chunks.
* With a **single-worker, single-threaded** uvicorn, a large batch of concurrent
  `/delay/1` requests must complete in little more than one second. A blocking
  handler, or a thread-pool bridge, will not pass.
* `/drip` must deliver its bytes progressively over the requested duration, not
  in one burst at the end.

## 5. Repository-wide scope

The migration is not finished when the Python package imports. The whole
repository must land in State B, coherently:

* **`httpbin/`** — the application: `core.py`, `helpers.py`, `filters.py`,
  `structures.py`, `utils.py`. The response decorators in `filters.py` are built
  on `decorator`, which is retired.
* **`pyproject.toml`** — dependencies, extras and metadata. Keep the project
  name `httpbin`, keep the version `0.10.2` (this is a migration, not a
  release), and keep setuptools as the build backend. The `mainapp` extra must
  describe the new server.
* **`requirements.txt`** — the pinned runtime lockfile used to build the image.
  It must describe the new closure. Every pin needs a hash: the `Dockerfile`
  installs it with hash checking. You can produce hashes offline from the wheels
  in `/opt/wheelhouse` (`pip hash`).
* **`Dockerfile`** — must build and run the ASGI service. It installs
  `requirements.txt` with `--require-hashes` and starts the service through one
  of the entry points in §2 point 4 (today that is `httpbin.bash`).
* **`Procfile`**, **`httpbin.bash`** — the entry points the project publishes
  today, and keeping them working is the least surprising thing to do. Whichever
  of them you publish must take its address from the environment — `HTTPBIN_HOST`
  and `HTTPBIN_PORT`, defaults `0.0.0.0` and `8080`, or the generic `HOST` and
  `PORT`. Both stages set both pairs and pick the port themselves; an entry point
  that hardcodes 8080 will not be the one they manage to start.
* **`tests/`** — the existing suite drives the app through Flask's test client
  and will not even import once Flask is gone. Port it; it must not import any
  retired package.
* **`tox.ini`**, **`.github/workflows/`** — the automation must reference the new
  stack, not the old one.
* **`setup.cfg`**, **`MANIFEST.in`** — ensure the package still ships its
  templates, static files, and any Swagger UI assets you add.

## 6. How the result is judged

Three things happen to the repository you leave behind, in order. First it is
**read**: the original tree and yours are compared to decide whether the migration
in section 2 actually happened. Then its **behaviour** is measured end to end over
HTTP, against the contract in section 4, from a clean install. Then it is
**attacked**: independent attempts are made to find a request the original answers
correctly and yours does not.

There is no partial credit anywhere in this ladder — not for a repository that
did not migrate, and not for one that migrated and left a check failing — and no
list of strings to avoid. Write the implementation you would ship.

## 7. Practical notes

* `python3`, `pip` and `pytest` on `PATH` are the **delivery** environment
  (`/opt/venv`): the allowlist only. Flask is not installable there — by design.
* Reinstall your work in place with
  `pip install --no-index --find-links /opt/wheelhouse -e .`
* Run your server the way the grader will:
  `HTTPBIN_PORT=8080 ./httpbin.bash`
* There is **no network**. Everything you need is already in the image.
* Leave your work in `/workspace/repo`. There is no patch to produce and nothing
  to submit: the directory is collected as-is when you finish.

## 8. Saying you are finished

When you consider the work complete, end your turn with a line containing
exactly:

```
DONE
```

on its own, and nothing after it.

This is how the run ends. Your session may be resumed more than once — a dropped
connection ends a turn without ending the job — and the only thing that
distinguishes "I am finished" from "my turn happened to stop here" is that line.
Without it a pause is read as a pause, you will be asked to continue, and work
you considered final may be continued past the point you wanted it to stop.

It is a statement about your own intent, not a claim to be graded, and writing it
neither asserts nor obtains anything about whether the migration is correct.
Nothing about your work is reviewed until the run is over, so there is no benefit
in withholding it and none in sending it early. Say it when you mean it.
