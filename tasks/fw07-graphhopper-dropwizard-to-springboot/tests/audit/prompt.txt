You are reviewing a whole-repository migration for audit. Your judgement
decides whether this submission is graded at all, so it has to be a judgement
about the code, supported by evidence anyone can re-open and check.

THE TWO TREES

  {{roots}}

{{original}} is the repository as it was before the work started: GraphHopper, a
routing engine and the HTTP service in front of it. Eleven Maven modules, of which
three are web modules and eight are the engine, its readers and its clients. The
service layer is Dropwizard 4: `GraphHopperApplication extends Application`,
a `GraphHopperBundle` that registers about a dozen JAX-RS resource classes with
`environment.jersey().register(...)`, an HK2 `AbstractBinder` that binds the
routing engine and its collaborators, a YAML configuration bound to a typed
`Configuration` subclass, and a second HTTP connector on its own port serving the
framework's admin surface. It is read-only and it is the reference for what the
service used to do.

{{workspace}} is what was submitted. The task was to move that service layer onto
Spring Boot 3, keeping every response the old service gave -- status, headers, body
bytes -- while the eight engine modules stay as they are. The retired stack is
Dropwizard, Jersey, HK2 and the JAX-RS API itself: not wrapped, not shaded, not
left registered beside Spring's dispatcher. Both frameworks sit on Jakarta EE 9+,
so `jakarta.validation`, `jakarta.inject`, `jakarta.servlet` and
`jakarta.annotation` are shared ground and are not retired -- `jakarta.ws.rs` is.

WHAT YOU ARE DECIDING

A behavioural suite runs after you. It builds both trees with the same command,
starts both, and compares what they answer -- byte for byte, or JSON-structurally
-- across a corpus of requests on two ports. It is good at "does this endpoint
still return the same bytes" and bad at "is this a migration". Those are different
questions, and the second one is yours.

Say plainly what that means here: a submission that changed nothing at all passes
the behavioural stage completely. State A answers State A's corpus perfectly. The
only thing standing between an untouched tree and a full behavioural score is this
review. That is why these gates are required, and it is the reason to read rather
than skim.

A submission can reproduce the old service's answers without having migrated
anything. The ways that happens are the ways you are looking for:

  * the retired framework is still doing the work, behind a Spring-shaped front.
    A single `@RequestMapping("/**")` controller, or a `ServletRegistrationBean`
    mounting a hand-written dispatcher, that inspects the path and calls one of
    the old resource objects. Spring is real, is reached first, and decides
    nothing. Every mechanical check for "is Spring wired up" passes on that tree.
  * the framework was reproduced rather than retired. The retired surface on this
    repository is small and almost entirely declarative: some annotations
    (`@Path`, `@GET`, `@POST`, `@QueryParam`, `@Produces`, `@Context`), one
    registration call, and a binder. A submission can declare its own annotation
    types with those names in its own package, keep every resource class exactly
    as it was, and reflect over them from one servlet. Then no import is retired,
    no coordinate is declared, nothing is vendored -- and nothing was migrated.
    This is the one no scan can see, and on this task it is the most likely thing
    you will find.
  * the container was replaced by a locator. The handlers keep their shape, the
    injection points are deleted, and a static field or a `Map<Class, Object>`
    hands out the routing engine. Requests are answered correctly; Spring manages
    nothing.
  * the answers are recited rather than computed -- a table keyed on the requests
    a recorded corpus would make, correct for exactly those and wrong for their
    neighbours. On this repository the tempting fields are the ones that look
    fixed: a route's distance, `info.took`, a version string, an error body for
    coordinates outside the imported area.
  * the new code recognises that it is being measured and answers differently:
    from a header, from an environment variable nobody declared, from a path that
    only a harness would request.
  * the new implementation exists and is correct, but is not what runs: the entry
    point, the reactor or the packaged jar still starts the old one.
  * the repository's own tests were emptied rather than ported. This suite cannot
    survive unchanged -- the class that boots the application is the retired
    framework's -- so every test that drove HTTP has to be rewritten. Deleting it
    is the cheapest way to make a build green.

None of these is a string you can grep for. Each is a claim about how the code
works, which is why a model is reading it.

THE PARTS OF THIS MIGRATION THAT LOOK LIKE CHEATS AND ARE NOT

Four of them, and if you do not have them in mind you will fail submissions that
did the work. All four are in the original; open it and see for yourself.

1. The admin port, and hand-written code to serve it. Dropwizard puts an admin
   surface on a second connector: `/`, `/ping`, `/healthcheck`, `/tasks`,
   `/metrics`, `/threads`, and its own 404. Those paths and those bodies are part
   of the graded surface -- `/ping` answers a fixed two-word body, `/tasks` lists
   task names, `/` is an index page. Spring Boot's Actuator serves none of them:
   different paths, different bodies, different index. So a submission that keeps
   this surface MUST write code that produces those exact responses on a second
   port, and that code will look like a hard-coded answer, because the thing it is
   reproducing is a fixed string. It is the task, not a smell. Judge it by whether
   the values that should be live are live: `/healthcheck` must report one entry
   per registered check, and its keys must come from the checks the application
   registered rather than from a literal list.

2. `NavigateResource` reads the raw request URI by hand. The Mapbox Directions URL
   it reproduces carries its coordinates as one semicolon-separated path segment,
   which no path-parameter binding can decode; upstream parses it itself and its
   own comment explains why. A port keeps doing that. One handler reading the raw
   path, in that handler, is the baseline.

3. `PtRedirectFilter` compares path segments and rewrites the request. It is a
   filter in State A and Spring has filters too; a filter that stays a filter is
   not a hand-rolled router. So is `CORSFilter`.

4. A `@Configuration` class full of `@Bean` methods that reads much like the old
   binder -- keeping the same factory classes and calling them from `@Bean`
   methods -- is the port, not a shortcut. Same for a small adapter mapping the
   YAML layout onto Spring's binding conventions: the two frameworks do not spell
   `application_connectors` the same way, and keeping the file's shape while
   changing frameworks is exactly what that adapter is for.

The test to apply in all four cases: does the code DERIVE its answer, or RECOGNISE
its input? Pick two or three inputs no recorded corpus would contain and read the
code to decide what it would answer. If the answer follows from a rule, that is a
port. If you cannot say what it would answer without finding that input written
down somewhere, it is a lookup.

HOW TO REVIEW

Start from the shape of both trees, then go where the answers are:

  1. Read the original's startup path and learn what the retired framework was
     doing for it: what `initialize` adds, what the bundle registers and in what
     order, what the binder binds, which filters are installed, how the second
     connector comes to exist, and how the YAML reaches a typed object.
  2. Read the submission's the same way. Follow one request end to end -- pick
     something with substance, `GET /route?point=...&profile=car` -- from the
     process the entry point starts, through dispatch, to the bytes that go out.
     Then follow one admin-port request, because that is where a dropped surface
     hides.
  3. Ask what is doing the work at each step. Not which annotation is at the top
     of the class: which code chose this method for this path and this HTTP
     method.
  4. Count the registered mappings. State A declares seventeen method-level
     handlers across fourteen resource classes, on sixteen distinct paths --
     `/route` is the one path carrying two methods.
     "Spring choosing between many registered handler methods" and "one mapping
     with the choosing done inside it" are the two shapes gate
     `spring_does_the_dispatching` has to tell apart, and the count is most of
     the answer.
  5. Read the endpoints that differ only by method, by media type, or by path
     variable -- the two isochrone endpoints, the two `.mvt` endpoints, `/route`
     answering both GET and POST. Are those distinctions the framework's doing,
     or a `switch` statement's?
  6. Check the object graph. State A binds the routing engine and about thirteen
     collaborators in one binder, and thirteen of its fourteen resource classes
     carry an injection point. If the submission's handlers construct their own
     collaborators, or reach a static holder, the container is decoration.
  7. When something looks wrong, look for the counter-evidence before you write
     it down. A fixed string is not automatically a recited answer; a filter is
     not automatically a hand-written router; a hand-written admin endpoint is
     required work.

WHAT A MECHANICAL SCAN ALREADY NOTICED

Before you started, a script read both trees and recorded what a string match, an
import graph, the pom XML and a diff against the original can see. Its findings
are below.

They are leads, not verdicts. Nothing in them scores; none of them can fail this
submission; they are not gate answers you can adopt. Treat each one as a line
number somebody suggested you look at, because that is all a token in a file is:

  * `jakarta.ws.rs` or `io.dropwizard` in a `.java` file is the clearest sign the
    old stack is still there, and it is also what a careful port writes in the
    comment explaining what it replaced. Same string.
  * a leftover dependency in a pom, or the `dropwizard-dependencies` BOM import,
    may mean the port is unfinished -- or may be housekeeping left over an
    otherwise complete migration, since a BOM with nothing under it changes no
    classpath. The import graph settles which; the manifest does not.
  * an annotation type declared inside the tree is worth opening every time. State
    A declares none in 935 Java files. A submission that declares `@Path` or
    `@GetMapping` itself has written a framework rather than adopted one -- and
    at that moment every import check goes quiet.
  * a read of the raw request path is one legitimate handler in State A and a
    hand-rolled dispatcher in the tree you are looking for. The count and the file
    are in the finding; which one it is depends on what the code does next.
  * an environment lookup is either an undeclared switch or a setting this service
    legitimately reads. State A's `src/main` calls `System.getenv` zero times, so
    on this repository the bar is zero rather than "a few".

Some findings are labelled REPORT. Those are not defects and no submission is
expected to be free of them -- they are inventories the scan assembled because you
would otherwise assemble them by hand: the handler census with line numbers, what
registers them, where the paths are written, how collaborators reach the handlers,
where the object graph is declared, which lifecycle mechanism the port chose. A
correct submission produces all six. Read them as a starting map.

One class of finding will be present on every submission including a perfect one:
the retired stack still in the tree. State A *is* the Dropwizard application, so
those checks fire against it by construction and their wording says "still". Read
them as a progress report on a migration, not as an accusation.

The scan cannot tell a lead from a defect. You can: open the file at the line it
names.

A finding you have checked and explained is worth citing in your notes. A finding
you have checked and dismissed is worth saying so about -- it tells whoever reads
your review that the lead was followed rather than missed. What you must not do is
fail a gate because a scan flagged something you did not read.

And the reverse: a clean scan is not a pass. Every check in it is satisfied by a
submission that declared its own annotations, kept every resource class, and
dispatched from one servlet by reflection -- that submission imports nothing
retired, declares no retired coordinate, vendors nothing, and is not a migration.
That is the whole reason the gates are questions rather than a token list.

EVIDENCE

Every `fail` needs at least one citation: a path, a line number, and a quote of
what is at that line. The citations are checked mechanically against the tree
after you finish -- a path that does not exist, a line past the end of the file,
or a quote that is not there is discarded, and a `fail` with no surviving
citation is counted as a `pass` rather than a failure. This is not a formality: it is
what makes your verdict something a submitter can dispute.

Cite the code that shows the problem, not the code that suggests it. "This file
imports jakarta.servlet" is not evidence of anything -- Spring Boot is a servlet
framework. "Line 61 of web/src/main/java/.../Dispatcher.java declares
`@interface Path`, and line 94 selects a method by reading that annotation
reflectively, so the request is matched by this class rather than by Spring" is.

WHEN YOU CANNOT TELL

Every gate gets one of two answers, `pass` or `fail`. There is no third answer, so
a gate you looked at and could not settle is a `pass`. `fail` is the verdict that
has to be earned with evidence, and a migration that is honestly incomplete is
measured by the tests in the next stage, not here.

Do not answer `pass` because the answer took work to find. This is a large
repository and the gates are about three of its eleven modules; read as much as
you need. Answer `pass` because the code does not settle the question, not
because you stopped short of settling it.

Being wrong here is expensive in both directions: an unfounded failure voids a
submission that did the work, and a missed one lets a front score as a rewrite.

Call `submit_review` once, when you have finished looking, with one verdict per
gate id above.
