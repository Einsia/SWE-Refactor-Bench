# The scan's runner, and nothing else.
#
# Four packages, hash-pinned, installed --no-deps: this is a test runner for checks
# that open files and read them.  Nothing on this list can build the submission, and
# that is the point of keeping it this short.  The stronger guarantee is in the
# Dockerfile, which installs no JDK and no Maven -- but a dependency list that could
# reach a build is worth avoiding on its own.  The moment an HTTP client or a JVM
# appears in this image, a scan module could start the service and compare it against
# something, and stage 1's claim -- that it observed the code without ever running it
# -- stops being structurally true and becomes a promise about what the checks happen
# to do today.
#
# No PyYAML, unlike what this repository's own build would need.  Two modules do read
# YAML: `wiring` looks at how the configuration object arrives from a file, and
# `provenance` checks the yml files for the rig's placeholders.  Both read those files
# as text, by line, and that is the correct reading -- what matters is whether
# @APP_PORT@ appears in a delivered file and whether something in src/main parses the
# document itself, not what the document deserialises to.  Parsing it here would
# answer a question nobody asked and would make a malformed config a scan crash
# instead of a finding.
#
# No pytest-timeout either, which the behavioural stage does install.  There it is not
# optional: that suite holds open sockets to two live servers and a submission that
# accepts a connection without answering would hang the stage.  A scan reads 935 Java
# files and 11 poms off a read-only mount; there is no socket and no clock, and the
# suite-level `default_timeout_sec` in scan.toml is the only bound that could matter.
#
# The versions are the ones tests/behavioural/requirements-runner.txt pins, so the
# scan runs on the same pytest the behavioural suite does and there is one version of
# the runner to reason about across the task.  Both hashes are listed for each
# package -- wheel and sdist -- because this image installs from a different base than
# the behavioural one, which is built on the Maven/Temurin image, and pip is free to
# prefer either artefact.
#
# Installed with --require-hashes, so a substituted artefact fails the image build
# rather than the grading run.
