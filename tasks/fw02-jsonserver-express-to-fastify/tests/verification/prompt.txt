TASK {{task}} -- find what the migration got wrong.

json-server is a REST API generated from a JSON file: point it at a database, and
every top-level key becomes a resource with filtering, sorting, pagination,
relationship expansion and the four write methods. The original is json-server
0.17.4 on Express 4 with the usual connect middleware stack -- body-parser,
compression, cors, morgan, method-override, express-urlrewrite, errorhandler --
built through babel and started through the executable its own package.json
declares. The submission is supposed to be the same service, reimplemented
natively on Fastify 5, with the whole Express stack removed and every observable
behaviour preserved.

Preserved means byte for byte where it can be: same status codes, same bodies
(JSON indented by two spaces, no trailing newline), same semantic headers,
including the weak ETag Express computes and the Link header its pagination
emits. It has already been checked that the migration is real -- the old stack is
gone, not wrapped -- and that a large recorded corpus of requests still gets the
right answers. Your job is the part that corpus cannot do: find a request nobody
thought to record.

THE TWO TREES

  {{original}}     the original service, Express 4 + connect middleware
  {{submission}}   the submission, which claims to be the same service on Fastify

Your tools address these by name: {{roots}}. The submission is the root called
`workspace`. Both are complete repositories, and both are read-only to you -- you
attack them over HTTP, not by editing them.

HOW A CANDIDATE IS RUN

Write a pytest file and hand it to `try_test`. For each tree, the runner copies
it, installs its declared dependencies offline, runs its build script, starts it
through the launcher the repository publishes, waits for it to answer, and runs
your file against it. Both trees are started against the same seed database and
the same rewrite-rule file -- the grader's copies, not the tree's -- so a
difference in the data is never the reason two answers differ. You are told the
outcome on each tree separately.

Your file gets one thing from the environment:

    SRB_BASE_URL   e.g. http://127.0.0.1:41234 -- the running target

`pytest` and the Python standard library are available. Nothing else is --
deliberately no httpx and no requests, because a client that transparently
decompresses a body or normalises a header would hide the differences most worth
finding here. `http.client` shows you the bytes. Do not read either tree from
inside the test and do not import anything out of it: what is being graded is a
service, and a test that opens a file is measuring a repository.

Exit status is the verdict: zero means your test passed against that tree,
non-zero means it failed. pytest does this for you.

WHAT A USEFUL CANDIDATE LOOKS LIKE

It has to pass on the original and fail on the submission. Both halves matter,
and the first is where most attempts die: a test that fails on both trees has
found a bug in the test, or a behaviour the original never had. Run every idea --
you have budget for many, and one call tells you which of the four outcomes you
got.

Then it has to assert on something that was promised. The scope below is
json-server's public contract, and a divergence outside it is thrown out on
review no matter how real it is. Two servers this different disagree about the
Date header, about header casing, about when a response is chunked; all of that
is excluded, and none of it is worth a candidate.

WHERE REWRITES OF THIS KIND ACTUALLY FAIL

Not on the main path. `GET /posts` and `POST /posts` work in every submission,
because they are the first thing anyone tries and the first thing anyone tests.
What gets left out is:

  * Headers that are computed rather than copied. The ETag is Express's weak
    format -- a hex body length, a hyphen, 27 characters of base64 SHA-1 -- and
    Fastify's own etag plugin emits a different shape entirely. The Link header
    has four rels in a particular order with a particular spelling. X-Total-Count
    appears on some reads and not others.
  * The second and third parameter of a query that mostly gets called with one.
    `_page` with `_sort`. `_limit` with `_start` and `_end`. `_embed` and
    `_expand` together. A repeated key. A dotted path into an object that does
    not exist.
  * Middleware behaviour the original inherited without writing down.
    body-parser's strict mode, and what it does with a top-level scalar.
    compression's size threshold. express-urlrewrite's treatment of a target that
    already has a query string. serve-static's index resolution. The original's
    author did not implement these; the submission's author had to.
  * Whole flags that are documented and rarely used. `--read-only`. `--delay`.
    `--id`. `--foreignKeySuffix`. `--static` with a second document root. And
    what happens when two of them are set at once.
  * Behaviour that is surprising, and therefore likely to have been tidied up.
    Three of these are documented in the task: two flags that do nothing while
    their aliases work, a DELETE that throws under a renamed id field, and an
    `_expand` that throws on a collection with no foreign key. A submission that
    made any of them behave sensibly changed what the service does.
  * Error paths. What comes back for a malformed body, a string where a number
    goes, an id that does not exist, a method a route does not take, a path that
    climbs out of the static root.

Read the original's implementation of whatever you are attacking before you write
the test. Its source is in front of you, and it -- not your expectation of what a
REST API should do -- is the standard your test has to meet first.

REPORTING

If you find a divergence that holds up, report it with the candidate name and a
description of what the submission gets wrong in terms of behaviour, plus which
part of the contract it violates.

If you do not, report that you found nothing, and say what you tried and where
you looked. That is a real result -- it is what a sound submission is supposed to
produce -- and a claim you cannot support is worth nothing more.
