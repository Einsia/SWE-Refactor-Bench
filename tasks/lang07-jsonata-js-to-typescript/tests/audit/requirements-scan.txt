# The scan's runner, and nothing else.
#
# Four packages, hash-pinned, --no-deps: this is a test runner for a set of checks
# that open files, hash them, lex their string literals and read their first four
# bytes.  Nothing here can import, configure or build the submission, and that is
# the point of keeping the list this short -- the moment an HTTP client or a
# framework appears in this image, a scan module could start a service, and stage
# 1's whole claim is that it cannot.
#
# On this task the same argument runs through the runtime, and it is sharper here
# than on the other language pairs.  Both sides of this migration are `node`: State
# A is JavaScript and State B compiles to it, so any State A file that survived
# into a submission is an executable implementation reachable by `require`, with no
# build step and no network.  There is therefore no Node, no npm and no `tsc` in
# this image, and that absence is asserted at build time rather than assumed -- a
# scan module that could run `node` could run the submission's probe, in the one
# container in this benchmark with network access to the model API.
#
# The versions and hashes are the ones every stage-1 image in this benchmark pins,
# so `swerefactor.pytest_module` -- the plugin that turns a pytest run into the check
# records the harness reads -- runs against the pytest it was written for.  Stage 2
# of this task pins nothing here because it needs no pytest at all: its driver is
# plain Python on the image's own interpreter, which is why the two stages'
# dependency lists have nothing to reconcile.  Stage 3 pins its own list, because a
# candidate is a pytest file and the adversary writes it.
