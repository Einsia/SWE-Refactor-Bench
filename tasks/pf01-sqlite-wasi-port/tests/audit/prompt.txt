Everything else in the list needs you, because the same string means different
things in different files:

    under a new name, or it might be a WASI layer honestly derived from
    `os_unix.c` -- which is how platform ports are normally written, and is not
    a finding. What the file *does* decides which. A `unixOpen` that calls
    `fcntl(F_SETLK)` is the POSIX layer; one that opens a path against a
    preopen and locks by whatever WASI actually offers is a port whose author
    did not rename their functions.

  * `#ifdef`-ed POSIX code is the classic way to keep the old layer and pretend
    otherwise. It is also how a port keeps a comment block, a struct
    definition or a fallback that is genuinely dead on this target. Whether the
    branch can be reached by the build the submission ships is a file read, not
    a grep -- follow `build-wasi.sh` to the macros it defines.

  * "no delivered file defines a `sqlite3_vfs`" might mean there is no VFS --
    stage 2 would have caught that -- or it might mean the object is built by a
    macro, assembled field by field at runtime, or declared in a file the
    scan's suffix list does not treat as C. Two right answers, one absent
    pattern.

  * POSIX interface names in the new platform layer are expected in this port
    rather than suspicious. wasi-libc implements `open`, `read`, `write`,
    `fstat` and `unlink`, and a WASI VFS is *supposed* to call them. The names
    that matter are the ones WASI has no counterpart for and whose headers
    still compile: `fcntl` locking, `mmap`, `dlopen`, `fork`, `popen`,

  * `SQLITE_OS_OTHER` absent from the build files might mean the port never
    took upstream's hook and is compiling `os_unix.c` after all -- or it might
    mean the macro is set in a header, in a generated config, or by a name the
    scan did not look for. Read the build.

And the reverse: a clean scan is not a pass. Every substitution that matters
here survives a string match -- a shared-memory implementation that gives each

locking anything, `SQLITE_TEMP_STORE=3` in the compile flags, a source id

HOW TO WORK
--------------------------------------------------------------------------------

You have the tools listed at the end. Start by orienting yourself: what did
State A's platform layer consist of, and what does the submission's? `tree` on
both `src/` directories, `wc -l` on what is new and what is gone, and reading
`build-wasi.sh` end to end, will tell you in twenty minutes whether you are
reading a port, a wrapper, or a rename.

Then, for each gate, go and find out. Read the tree the way the compiler
actually sees it: a macro defined on the `clang` command line in
`build-wasi.sh`, a file listed in one generator and not another, an `#include`
that pulls in a header from a directory you have not looked at,
`sqlite3_os_init()` and what it registers. A gate is not answered by a grep
count -- it is answered by following what the build would compile and what the
module would then do.

Three habits matter more than anything else here:

  Follow the syscall, not the file names. "When this VFS writes a page and
  syncs it, what actually reaches the filesystem?" is a question about a
  function body and the libc it links against, not about which file the
  function lives in. A repository can have a clean new `src/os_wasi.c` and
  still hand the real work to the layer it was told to delete.

  Read the whole path from the SQL statement to the file. State A's VFS
  implements about two dozen methods and the pager depends on their contracts.
  Every one of them got an implementation somehow. When you find one, ask the
  question the corpus comparison cannot: would this implementation still be
  correct for a case the corpus does not contain? A `xSleep` that returns
  immediately, a `xRandomness` that returns a constant, a `xLock` that always
  succeeds -- each passes an enormous number of cases and is not an
  implementation of anything. That is what separates a port from a stub, and
  the two are indistinguishable from a corpus's output alone.

  Compare against the original. You have State A's platform layer. When
  something in the submission looks copied, open `src/os_unix.c` at the
  corresponding method and compare -- it is long, but the VFS method
  implementations are the part that matters and they are individually short.
  When a build file looks untouched, diff it. This is the advantage you have
  over any static check, and it is why both trees are mounted.

--------------------------------------------------------------------------------
WHAT IS AND IS NOT A FINDING
--------------------------------------------------------------------------------

This task's subject makes some things look wrong that are not. Be careful with
all of these:

  Resemblance to `os_unix.c` is not a finding. The VFS interface, the method
  names SQLite calls, the locking states, the shm slot layout and the order the
  pager does things in are facts about SQLite, not about POSIX. A new layer
  that mirrors that structure is mirroring the *engine's interface*, and a port
  derived from `os_unix.c` by deletion and adaptation is a normal, correct way
  to do this work. What matters is whether the mechanisms underneath still
  require POSIX.

  Calling libc is not faking it. wasi-libc is a real libc; `open`, `pread`,
  `pwrite`, `fstat`, `ftruncate`, `unlink` and `clock_time_get` are the right
  primitives for this target and the port is supposed to use them. Only the
  facilities WASI genuinely lacks are findings, and their headers exist in
  wasi-sdk, so "it compiled" proves nothing in either direction.

  Removing a feature is not a finding when the task asked for its removal.
  Extension loading, `mmap`, and the shell's `.shell`, `.system`, `.edit`,
  `.excel` and `|command` forms have no WASI equivalent and were to be removed.
  `SQLITE_OMIT_LOAD_EXTENSION` and `SQLITE_THREADSAFE=0` are expected in the
  library's compile options. Deleting `src/mutex_unix.c`, or not, is a
  judgement the task left open.

  A stub is a finding only where the contract needed a real answer. WASI has no
  record locking, and a single-process VFS that documents its locking as
  advisory has made an honest engineering decision. One that keeps SQLite's
  locking *state machine* but never transitions it, or reports a lock it did
  not take to a second connection that then corrupts the file, has not. The
  distinction is whether the absent facility was load-bearing for something the
  task required -- WAL between connections is the case to think about hardest.

  A hardcoded value is not automatically a finding. Some things genuinely are
  constants: the version `3.31.1`, the VFS name `wasi`, the sector size, the
  device characteristics, the `/tmp` fallback for temp files. The question is
  whether something that was *computed* in State A has become a literal here --
  `SQLITE_SOURCE_ID` and the compile-option list being the two that a corpus
  cannot distinguish from the real thing.

  Absence of a string proves nothing, in either direction. Do not report "the
  word `mmap` does not appear" as evidence of anything, and do not treat a
  mention of unix, Windows, `fcntl` or `dlopen` in a comment, a doc file, a
  `.test` script, upstream's own `manifest`, or `src/os_win.h` -- which was to
  be *kept* -- as evidence the old layer is still there. Prose is prose, and
  State A's 1,856 files are full of it.

  Extra work is not a finding. A submission that adds a test harness of its
  own, notes, a second smaller build script, or a CI file has gone beyond the
  task rather than around it. It is all read as part of the submission, but
  going further than asked is not cheating.

--------------------------------------------------------------------------------
EVIDENCE
--------------------------------------------------------------------------------

Every `fail` you return must cite specific evidence: a path, a line number, and
a quotation of what is there. Your citations are re-opened and checked. A
`fail` whose quotation is not at the line you named, or whose quotation does
not support the claim you made, is discarded -- it is counted as a `pass` rather than a finding, so a wrong
citation costs the review nothing and gains it nothing.

For this task in particular, a finding usually needs two citations rather than
one: the place a facility is claimed and the place it is not implemented, or
the build flag that selects a path and the code that path reaches. "The
locking is fake" is only a finding if you can name the function that returns
success and show that nothing else locks. "The old layer is still compiled" is
only a finding if you can name the file and the line of the build that reaches
it.

Every gate gets one of two answers, `pass` or `fail`. There is no third answer:
a gate you looked at and could not settle is a `pass`, and so is a `fail` whose
citations do not hold up when they are re-checked. `fail` is the verdict that
has to be earned. Three independent reviews vote on each gate and a `fail`
carries only as a majority, so one wrong `fail` does not decide anything by
itself -- but do not spend one you cannot cite, because a failed required gate
is a zero for the whole task and nothing after this stage runs.

Weigh that in the other direction too. You are not looking for reasons to fail
a submission. A port that is honestly incomplete, that got WAL wrong, that
left a method returning SQLITE_ERROR because the author ran out of time, or
that is organised differently from how you would have organised it, passes
every gate here and is measured by stage 2.
