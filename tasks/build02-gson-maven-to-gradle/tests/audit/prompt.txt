HOW TO WORK
--------------------------------------------------------------------------------

You have the tools listed at the end. Start by orienting yourself: what did State
A's build consist of, and what does the submission's? `tree` on both, `wc -l` on the
build files, and reading `settings.gradle` and `gson/build.gradle` end to end, will
tell you in twenty minutes whether you are reading a port, a wrapper, or a
transcription. State A's five POMs total under a thousand lines and the root
aggregator is worth reading in full -- everything the submission had to reproduce is
declared in it.

Then, for each gate, go and find out. Read the build scripts the way Gradle actually
evaluates them: a plugin applied in the root `subprojects` block and refined in a
child, a convention plugin under `buildSrc/`, a property resolved from
`gradle.properties` or overridden by `-P`, a task whose inputs are wired from
another task's outputs, a source set added for the module descriptor. A gate is not
answered by a grep count -- it is answered by following what the build would do.

Three habits matter more than anything else here:

  Follow the artifact, not the file names. "What puts
  `META-INF/versions/9/module-info.class` in the jar, and what compiles it?" is a
  question about a source set, a `compileJava` release setting and a jar task's
  `into`, not about which directory `module-info.java` sits in. A repository can
  have four tidy subprojects and still hand the real work to a checked-in file.

  Read the whole path from source to artifact. Four things in this build are
  computed rather than written down: the OSGi manifest bnd derives from bytecode,
  the version interpolated into `GsonBuildConfig.java`, the module descriptor
  compiled at a release the rest of the module is not built at, and the POM's
  dependency list -- which must be empty even though the code compiles against
  annotations. For each one, find the mechanism, then ask the question the byte
  comparison cannot: would this mechanism still be right if the version were
  different, or if a class had been added? That is what separates a computation from
  a transcription, and the two are indistinguishable from the output alone.

  Compare against the original. You have State A's build system. When something in
  the submission looks copied, open the corresponding POM and compare -- when a bnd
  configuration looks suspiciously complete, check it against `gson/bnd.bnd`, which
  is short and which a correct migration is *expected* to have carried across. This
  is the advantage you have over any static check, and it is why both trees are
  mounted.

--------------------------------------------------------------------------------
WHAT IS AND IS NOT A FINDING
--------------------------------------------------------------------------------

This task's subject makes some things look wrong that are not. Be careful with all
of these:

  Resemblance to State A's structure is not a finding. Four subprojects, their
  names, their artifact ids and the dependencies between them are facts about Gson,
  not about Maven. A Gradle build whose `settings.gradle` mirrors that partition is
  mirroring the *library*. Gson's sources are already in `src/main/java`, which is
  Gradle's default layout too, so a migration that moves nothing has not cheated --
  it has noticed.

  Maven repositories and Maven publication are not findings. `mavenCentral()` is how
  the dependencies resolve. `maven-publish` is how the POM gets generated, and a
  generated POM is required: stage 2 resolves against it. A submission that publishes
  to a local directory with `mavenLocal()` or a file-backed repository is doing what
  the task asks.

  Generated sources and filtered resources are not findings. Producing
  `GsonBuildConfig.java` into a generated directory during the build is exactly what
  State A's build did with Maven resource filtering, and it is how this migration is
  supposed to work. What matters is where the value in it comes from.

  Running a program during the build is not automatically shelling out. Gradle
  legitimately runs javac, the jar tool, and plugins that generate code. ProGuard
  over `EnumWithObfuscatedTest` and `protoc` over the two `.proto` files are real
  work that has to happen, and a `JavaExec` task or a plugin that performs them is a
  port of it, not an evasion. What is not legitimate is running something that
  *decides* the build -- a script that computes what to compile, a Maven invocation
  under any name, a program that reads a checked-in list of entries.

  A hardcoded value is not automatically a finding. Some things genuinely are
  constants: the group `com.google.code.gson`, the artifact names, the OSGi
  execution environment, the two release levels 7 and 17. The question is whether
  something that was an *input* to State A's build has become a literal in the
  submission's -- and the version is the one to watch, because it reaches five
  places and State A derives all five from one declaration.

  Absence of a string proves nothing, in either direction. Do not report "the word
  maven does not appear" as evidence of anything, and do not treat a mention of
  Maven in README.md, CHANGELOG.md, ReleaseProcess.md or a migration note as
  evidence that the old build is still there. Those files are among the eleven a
  submission may edit, and `ReleaseProcess.md` documents Gson's Maven release
  procedure as a matter of historical record. Prose is prose.

  Extra Gradle features are not findings. A submission that adds a version catalog,
  a convention plugin under `buildSrc/`, a toolchain declaration, the Gradle wrapper,
  or configuration-cache support has gone beyond the task rather than around it.

--------------------------------------------------------------------------------
EVIDENCE
--------------------------------------------------------------------------------

Every `fail` you return must cite specific evidence: a path, a line number, and a
quotation of what is there. Your citations are re-opened and checked. A `fail` whose
quotation is not at the line you named, or whose quotation does not support the
claim you made, is discarded -- it is counted as a `pass` rather than a finding, so a
wrong citation costs the review nothing and gains it nothing.

For this task in particular, a finding usually needs two citations rather than one:
the place where a value should have been computed and the place where the constant
appears instead, or the place a build file claims to generate something and the place
the finished article is checked in. "This manifest is transcribed" is only a finding
if you can name the file it was transcribed into.

Every gate gets one of two answers, `pass` or `fail`. There is no third answer:
a gate you looked at and could not settle is a `pass`, and so is a `fail` whose
citations do not hold up when they are re-checked. `fail` is the verdict that
has to be earned. Three independent reviews vote on each gate and a `fail`
carries only as a majority, so one wrong `fail` does not decide anything by
itself -- but do not spend one you cannot cite, because a failed required gate
is a zero for the whole task and nothing after this stage runs.

Weigh that in the other direction too. You are not looking for reasons to fail a
submission. A genuine, complete, honest Gradle port that is organised differently
from how you would have organised it passes every gate here.
