# The behavioural suite's runner, and nothing else.
#
# Ten modules, ~2,680 checks, all of them reading files a Gradle build wrote: jars,
# class files, manifests, a published repository, JUnit XML. The readers are in
# lib/ and use the standard library only -- zipfile, struct, xml.etree, hashlib --
# so pytest and its three dependencies are the whole list.
#
# Deliberately absent: any HTTP client, any build-tool binding, any JVM bridge. The
# image has no network, and a module that wanted to reach one would be measuring
# something other than the submission. The jar readers are hand-written against the
# formats rather than pulled from PyPI for the same reason a byte comparison is the
# instrument here: a library that tolerates a malformed entry would hide exactly the
# defect this stage exists to find.
#
# --require-hashes --no-deps, and the same versions stage 1 pins in
# requirements-scan.txt. The two stages run the same pytest on purpose: collection
# behaviour decides what a check id is, and a scan module and a behavioural module are
# the same shape by design -- one that drifted onto a different runner could collect
# a different number of checks from the same file.
